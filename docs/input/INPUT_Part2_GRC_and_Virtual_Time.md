# PART A: GRC GENERATION

## A1. Core design: two versions of every GRC record

The most important idea in this part:

```text
REALITY  (hidden)   what is actually true in the enterprise, derived from the Scenario Spec
RECORDED (visible)  what the organization's GRC documents say, derived from REALITY
                    through (1) normal human imperfection and (2) injected flaws
```

- GRC is never invented independently. It is **derived from the spec** (assets, services, weaknesses, controls actually present), so it is internally consistent by construction.
- The recorded version is the reality passed through a **degradation layer**. Every difference between recorded and reality is either baseline noise (small, harmless, unledgered but bounded) or an **injected flaw** (rare, ledgered in the hidden truth plane).
- The AI Engine only ever sees RECORDED. The reality and the flaw ledger stay hidden and are used for evaluation. This directly supports the "AI finds gaps in GRC" goal, because a gap is now an exact, known, measurable thing.

```text
Scenario Spec ---> GRC REALITY ---> degradation (noise + flaws) ---> GRC RECORDED (Engine input)
                       |                         |
                       +-- hidden truth          +-- flaw ledger (hidden)
```

## A2. Scope: which GRC artifacts

You asked whether Asset Inventory + Risk Register is enough. Answer: **no, it is not enough**, for a concrete reason. The Engine's outputs are about controls, exceptions and risk changes ("modify a control status", "recommend a governance action"), and the existing Dataset Contract and Engine already consume controls, exceptions and time-valid context. Without a control register the AI would have nothing to recommend changing.

| Tier | Artifact | Why | In v1 |
|---|---|---|---|
| Must | **Asset inventory** (with business context) | Foundation; criticality drives priority | Yes |
| Must | **Risk register** | Core of SOC-to-GRC risk movement | Yes |
| Must | **Control register** (state per control, links to assets/risks) | Engine recommends control changes [PROTO contract: controls.json] | Yes |
| Must | **Policy exceptions** (time-bounded) | Cheap, naturally time-dependent flaws, already in contract | Yes |
| Should | **Incident register** (past incidents, status, dates) | Historical likelihood, reopened/stale incidents, lessons-learned gaps | Yes (small) |
| Should | **Findings / remediation tracker** (vulnerability findings with owner, SLA, due date, status) | Bridges scanner posture to GRC; SLA breaches are a classic governance gap | Yes (small) |
| Later | Control-to-framework mapping (ISO 27001 / NIST CSF / CIS) | Needed for language translation across frameworks; contract has `control_mappings.json` | Yes, generated by lookup table (cheap) |
| Later | Vendor/third-party register, audit findings, KRIs, policy documents | Valuable but secondary | No for v1; schema slots reserved |

So v1 = 4 must-haves + 2 small "should" + framework mapping table. The extra four artifacts are small tables derived from the same reality graph, so the added cost is low.

## A3. Organizational GRC style (supports "GRC language translation")

Real organizations describe the same facts differently. Per scenario, `seed_grc` samples a **GRC style profile**:

| Dimension | Options |
|---|---|
| Risk scale | 5x5 matrix, 3-level (L/M/H), 1-10 numeric, qualitative text only |
| Control framework vocabulary | ISO 27001 Annex A style, NIST CSF style, CIS Controls style, home-grown names |
| Asset criticality scale | 1-5, Tier 0-3, "business critical / important / normal", CIA triad ratings |
| Naming/tag conventions | asset IDs, owner naming, department naming, date formats |
| Completeness habit | by security maturity (low maturity: sparse fields; high: complete) |
| Review cadence | monthly / quarterly / annual / "when someone remembers" |

The Engine (and the dashboard) must translate these into one internal representation. This directly tests the "translation" function from the original spec. The export includes `scale_definition.json` for each scenario, because a number is meaningless without its scale (real organizations do document this).

## A4. Asset inventory generation

**Reality** comes straight from the spec: every container/host, role, zone, IPs, OS, services, owner role, business unit, data it stores, internet exposure.

**Business context derived (not random):**
```text
criticality   = f(role, data_sensitivity, business_process, dependency fan-in)
                e.g. DB with customer records and many dependents -> 5; kiosk workstation -> 1
data_class    = from the service recipe + the seeded data (public/internal/confidential/regulated)
owner         = sampled from the generated identity pool by department
exposure      = from the topology (internet-facing path exists)
```
Fan-in matters: an otherwise unremarkable host that many services depend on gets higher criticality, so the model has to look at topology, not just labels.

**Recorded version:** same fields in the organization's style, with baseline noise (e.g. criticality off by one on about 5-10% of low-maturity assets, owner missing for some, free-text department variants) and optionally injected flaws (A7).

Fields follow the existing contract [PROTO]: `asset_id, hostname, role, zone, IPs, OS profile, criticality, owner, business_unit, business_process, data_sensitivity, internet_exposed, service_ids, wazuh agent identity`, plus new: `last_reviewed_at`, `recorded_at`, `source_of_record` (CMDB, spreadsheet, scanner-discovered).

## A5. Risk register generation

**Risk templates** (a catalog, written once, applied by rules). Each template has: applicable asset roles, threat scenario, relevant weaknesses/controls, and impact driver.

Examples:
```text
R-DB-01   Unauthorized access to customer database       (roles: DB; ties to: weak auth, no segmentation, no MFA)
R-WEB-01  Web application compromise                     (roles: web/app; ties to: injection weakness, WAF absent, outdated package)
R-IDN-01  Credential compromise of privileged account    (roles: directory/admin; ties to: brute-force exposure, no MFA, shared keys)
R-FIL-01  Ransomware on file/backup servers              (roles: file/backup; ties to: backup isolation, EDR absent)
R-NET-01  Lateral movement across zones                  (ties to: flat policy, exceptions)
R-INS-01  Insider data exfiltration                      (ties to: excess privilege, no DLP/logging)
R-AVL-01  Service outage of critical business process    (ties to: no redundancy, unpatched)
R-SUP-01  Third-party / update channel compromise        (optional)
```

**Reality computation:**
```text
likelihood_reality = f(weaknesses present on linked assets, exposure, control effectiveness,
                       threat activity in the scenario timeline)
impact_reality     = f(asset criticality, data sensitivity, business process dependency)
inherent_risk      = likelihood * impact
control_factor     = effectiveness of controls that actually work (from reality, not from paper)
residual_risk      = inherent_risk * control_factor
```
Formulas are fixed and versioned (`grc_formula_version`). Because they use reality, the register can be re-derived at any virtual time as weaknesses appear and disappear.

**Recorded version:** the organization's estimate. It is built from reality with baseline human error (round to the scale, estimate lagging behind changes, optimistic bias in low maturity) then converted into the scenario's scale style. Each risk has owner, treatment (accept/mitigate/transfer/avoid), linked controls, linked assets, `last_reviewed_at`, `next_review_due`, status (open/closing/closed/accepted). Fields follow the contract [PROTO: `risk_id, asset/service, risk_scenario, likelihood, impact, raw_risk, control_factor, residual_risk, risk_level, treatment, linked_control_ids, snapshot_time, scoring_version`].

## A6. Control register and exceptions

- A control catalog (about 40-60 controls in v1, CIS/NIST/ISO-like, written once) with **applicability rules** (which asset roles/services each control applies to) and a **reality test** (what in the spec makes the control actually effective, e.g. MFA control effective only where MFA is enforced; segmentation control effective only where the zone policy denies the path).
- **Reality state:** implemented / partial / missing, computed per asset from the spec.
- **Recorded state:** what the register claims, normally equal to reality with baseline noise, with the contract's states: `implemented, partial, missing, not_assessed, compensating, exception`.
- Weakness modules (Part 1, section 3.4) carry an `enabling control` field, so every injected weakness automatically links to the control whose absence caused it. This gives us the "causal controls" truth needed for evaluation, for free.
- Policy exceptions: generated for a subset of control gaps with `valid_from`, `valid_until`, approver, compensating controls. Time-bounded by design, which makes them the cleanest source of time flaws (expired but still treated as valid).

## A7. Flaws: what they are, how rare, how they are injected

### A7.1 Rules

1. Rare, not constant: most scenarios have zero or few flaws.
2. Varied in **obviousness level**, from blatant to situational.
3. Varied in **object type** (asset, risk, control, exception, link between them).
4. Time-aware: many only exist in a time window or only become visible later.
5. **Every flaw is discoverable or deliberately marked undiscoverable** (A7.4). We never create a flaw with no possible way to notice it and then grade the AI on missing it.
6. Every flaw is written to the hidden **flaw ledger**.

### A7.2 Levels

| Level | Meaning | Example |
|---|---|---|
| L1 Gross | Obvious on direct inspection | Customer DB recorded as criticality 1 |
| L2 Moderate | Visible by comparing two GRC records | Risk register lists asset that the asset inventory marks decommissioned |
| L3 Evidence-based | Needs telemetry to catch | Host with a Wazuh agent and active traffic that is absent from the inventory (shadow IT) |
| L4 Situational / time-dependent | True only in a window, or created by change | Criticality was correct, then business process changed on day 40 and nobody updated it; policy exception expired on day 55 but control still treated as "exception" |
| L5 Compound / systemic | Several small issues that together matter | Risk scores across the register systematically 1 level too low for the whole DMZ zone; controls "implemented" on paper only for assets inside one stale scope |

### A7.3 Flaw catalog (v1)

**Asset inventory**
- Missing asset (shadow IT / unmanaged host) [telemetry-visible]
- Ghost asset (decommissioned, still listed)
- Wrong criticality (too low = dangerous, too high = waste), gross or subtle
- Wrong owner or no owner
- Stale network data (wrong IP/zone/hostname)
- Wrong OS/software version
- Missing data classification on a sensitive asset
- Duplicate or conflicting entries
- Wrong internet-exposed flag

**Risk register**
- Known weakness with no corresponding risk
- Risk linked to wrong asset or missing asset link
- Stale risk score (not updated after a real change or incident)
- Likelihood/impact inconsistent with asset criticality
- Residual risk overstated by a control that is not effective in reality
- Risk accepted with expired approval/exception
- Overdue review/treatment, orphan owner
- Duplicate risks with inconsistent scores
- Mixed scales (a score recorded under another scale)

**Control register**
- Control marked implemented but absent/ineffective on some assets (paper control)
- Control marked missing though actually present (understated posture)
- Control scope too narrow (covers some assets, silently not others)
- `not_assessed` for a long time on a critical asset
- Compensating control that does not actually compensate

**Exceptions / remediation / incidents**
- Expired exception still active
- Exception without compensating control
- Finding past remediation SLA with no escalation
- Incident closed but root-cause weakness still present
- Incident missing from register though telemetry shows it happened (and succeeded)

### A7.4 Detectability classes (fairness of evaluation)

| Class | How it can be noticed | Share (approx.) |
|---|---|---|
| D1 Internal inconsistency | Contradiction between two recorded GRC artifacts | 30% |
| D2 Telemetry-evident | Contradiction between GRC and Wazuh/Suricata/scanner/topology data | 40% |
| D3 Time-evident | Contradiction only visible by comparing dates and the timeline (stale, expired, overdue) | 20% |
| D4 Undetectable by design | Not visible from any provided data (control group) | 10% |

D4 exists on purpose: it measures whether the AI makes confident claims or abstains when it cannot know. D4 flaws are excluded from "missed flaw" scoring and used for calibration scoring.

### A7.5 Rates

A flaw budget is drawn per scenario from a Poisson-like distribution whose rate depends on security maturity:

| Maturity | Clean scenario (0 flaws) | Typical flaw count | Cap |
|---|---|---|---|
| High | ~45% | 0-2 | 3 |
| Medium | ~30% | 1-3 | 5 |
| Low | ~15% | 2-5 | 8 |

Level mix within drawn flaws: L1 about 15%, L2 25%, L3 25%, L4 25%, L5 about 10%. Rates are parameters in a config file and are tuned after we see how many flaws the Engine can find (too easy or impossible both make the benchmark useless).

### A7.6 Injection mechanism

Flaws are applied by `flaw modules` operating **only on the recorded layer** after the reality layer is built, so reality stays clean and consistent:

```text
flaw module:  id, level, object_types, detectability_class,
              preconditions   (e.g. needs a DB asset with criticality >= 4)
              mutation        (what changes in the recorded view)
              time_window     (valid_from / valid_to in virtual time, or "from event X on")
              evidence_refs   (where in telemetry/GRC the contradiction can be seen)
              harm_if_ignored (low / medium / high)  <- feeds evaluation
              reference_action (what a good analyst/AI would flag or recommend)
```
The preconditions step guarantees realism (no "critical" flaw injected where it doesn't matter). The ledger entry written is:

```text
flaw_id, scenario_id, module_id, level, detectability, object_ref,
injected_at / active_window (virtual time), evidence_refs,
harm_if_ignored, reference_action, rubric_version
```

## A8. Time and GRC (bitemporal records)

Every GRC record carries two clocks:
- `valid_from / valid_to`: when the fact is true in the enterprise (virtual time).
- `recorded_at`: when the organization wrote it into the register (virtual time). The gap between them is the **lag**, which is the source of staleness.

Rules:
- The Engine only gets the **as-of** view: records with `recorded_at <= T` (no future leakage). This matches the existing "time-valid context" [PROTO: pre_activity_context, context_history].
- GRC changes happen as timed events on the master timeline (A9 and Part B): asset added/decommissioned, criticality changed, control state updated, exception granted/expired, risk reviewed, incident recorded, finding opened/closed. Each event writes an append-only line to `context_history.jsonl`.
- **Review cycle simulation:** each artifact has a cadence. A review event may fix, miss, or half-fix the recorded state. Lag distributions are heavy-tailed (most updates within days, some forgotten for months), longer for low maturity.
- **SOC-triggered GRC changes:** a real incident in the range triggers a GRC response event with a lag (register updated after 2 days, or never, which is itself a flaw type).
- Snapshots are exported at the start of every live episode, plus the full change log, plus a post-scenario retrospective snapshot [PROTO naming].

## A9. GRC generation pipeline

```text
1. read Scenario Spec (assets, services, weaknesses, controls present, identities)
2. build REALITY graph (assets, services, weaknesses, controls, dependencies)
3. build REALITY GRC (criticality, data class, risks via templates, control states, exceptions)
4. sample GRC style profile (scales, vocabulary, cadence, completeness)
5. build RECORDED baseline = reality -> style conversion + baseline noise
6. generate GRC timeline events (reviews, changes, exception expiries, incident responses, finding SLAs)
7. draw flaw budget; inject flaws via modules (preconditions, windows) -> flaw ledger
8. validate: schema, referential integrity (every link points somewhere unless the flaw says otherwise),
   flaw ledger consistent with recorded-vs-reality diff (auto-check: diff == baseline noise + ledger)
9. export RECORDED artifacts + hidden REALITY + flaw ledger
```
Step 8 is the safety net: an automated "diff audit" proves that every discrepancy between reality and recorded is accounted for as either bounded baseline noise or a ledgered flaw. No unexplained differences.

# PART B: VIRTUAL TIME (FINAL DESIGN)

## B1. What the problem really is

We need: (a) scenarios spanning weeks to months of virtual time, (b) timestamps in telemetry that are consistent across network, Wazuh, Suricata, applications, GRC and truth, (c) not waiting months of wall time, (d) long-running attack sequences and changes over time.

Hard fact: real services (Wazuh, Suricata, TCP, TLS, databases) are built for real time. Speeding up the clock (the "1 s = 1 month" idea) breaks timeouts, keepalives, packet timing and certificate checks. It cannot be done for the whole real stack.

So we **do not accelerate the real stack**. Compression comes from **skipping time**, not from speeding clocks.

## B2. Decision: two-layer time model

```text
LAYER 1: STATE TIMELINE  (simulated, instant)
   A discrete-event simulation of everything that changes slowly:
   GRC edits, asset adds/decommissions, patches, config drift, new accounts,
   exception expiries, CVE publication, review cycles, campaign stage scheduling.
   Cost: negligible. This is where "1 s = 1 month" is genuinely true.

LAYER 2: LIVE EPISODES   (real execution, real-time speed)
   Short windows (e.g. 15 min to 3 h of virtual time) where the real Docker range,
   Wazuh and Suricata run at normal speed and produce genuine telemetry.
   Between episodes the clock jumps forward to the next episode.
```

Example: a 120-day scenario with 12 live episodes of 30-60 min each: about 8 hours of real execution (can be run in parallel lanes), while Layer 1 covers the whole 120 days instantly. Compression ratio is reported per scenario.

## B3. Master timeline

Generated once from `seed_time` and stored as `timeline.jsonl` (the replication artifact for time).

```text
calendar:    start date, horizon (e.g. 30-180 virtual days), timezone, workweek, holidays (simple per-country list), shift pattern
state events: timestamp, type, target, payload   (Layer 1; applied to GRC, spec state, range config)
episodes:    id, virtual_start, virtual_end, purpose (baseline | attack-stage | post-change | quiet), planned activities
campaigns:   multi-stage attack plans whose steps are assigned to specific episodes
```

Everything in the project uses a single `VClock` class (`now()`, `schedule()`, `advance_to()`). No module may call the real `datetime.now()`. A static check in CI forbids it outside the clock module.

**Episode placement (how we choose when to look):**
1. Every attack-campaign stage gets an episode covering it (must).
2. Baseline episodes sampled across weekdays/weekends/night/day/month-end for normal variety.
3. Post-change episodes shortly after significant state events (patch, firewall exception, GRC change) so effects are observable.
4. Quiet episodes (no attack at all) at a healthy rate.

**Multi-episode campaigns:** a slow attack (recon on day 3, credential use on day 20, lateral movement on day 22, exfil on day 40) spans episodes. Attacker footholds persist (keys, accounts, files) because the environment **carries state between episodes** (B5).

## B4. Clock mechanics inside an episode

Per episode, the range runs at **1x speed with a constant offset**:
```text
virtual_time = real_time + offset(episode)
```
Implementation, in order of preference:

1. **libfaketime in offset mode** for all lane components (agents, Wazuh manager, application containers, traffic agents), set to the episode's virtual start date, then running normally. No speed multiplier. This is the simple, well-understood use of libfaketime, and it gives native timestamps in all text logs, auth logs, Wazuh alerts and application events. [MEASURE: confirm it works with the Wazuh daemons and sample services; confirm date-dependent behavior such as TLS validity and cron is consistent.]
2. **Suricata** timestamps come from kernel packet capture, not the faked clock, so Suricata output is shifted by the **known constant episode offset** in post-processing (structured JSON timestamp fields only, low risk). The same shift is the fallback for any component libfaketime cannot cover.
3. **Fallback (always works):** run the episode on real time, then retime structured outputs by the constant offset. Text-embedded timestamps (syslog strings inside `full_log`) are rewritten only through verified per-format rewriters. Used only if libfaketime fails the measurement.

Every episode ends with the **time-consistency validator** (B7).

## B5. Moving between episodes (the jump) and carrying state

State that must persist across episodes: database contents, user accounts and files, SSH keys and authorized_keys, application state, Wazuh agent registrations, FIM baselines, installed package versions, firewall rules, any attacker persistence.

**v1 mechanism (robust, matches the prototype):** each episode is a **deploy-from-state** run:
```text
end of episode N: quiesce, drain telemetry, snapshot persistent volumes + Wazuh agent keys/state
Layer 1 applies timeline events between N and N+1 to the snapshot
          (patch = swap service image version, firewall change = new rules file, new user = insert, etc.)
episode N+1: deploy the range from the updated snapshot with the new clock offset, health gate, run
```
The prototype already deploys fully per run, so this reuses proven machinery; the new part is state snapshot/restore and the reconciler that applies timeline events.

**v1.1 optimization (only if measured as safe):** keep the range running, `docker pause` all lane containers, change the shared offset file, unpause, so every process sees the forward jump at once, then discard the first minutes as warmup. This avoids redeploy cost. [MEASURE: clock-jump test: 1 manager + 2 agents + Suricata, jump 90 days, check agent reconnect, alert timestamps, FIM behavior, no crashes.] Adopt only if it passes; otherwise stay on v1. No further decision is needed either way.

## B6. Time and each subsystem

| Subsystem | Behavior |
|---|---|
| **Network** | Topology changes (new host, decommission, firewall exception, exception expiry) are Layer 1 events applied in the gap between episodes by the reconciler. Live changes inside an episode are rare and scheduled. Routing/policy always carries an `effective_from` virtual timestamp in the truth plane |
| **Wazuh / SOC** | Runs only in episodes. Archives and alerts carry virtual timestamps. Rule/agent coverage changes (maturity-driven, sensor outage) are timeline events. Between episodes there is **no telemetry at all**, and this is explicit (see below) |
| **Suricata** | Same episodes; timestamps shifted by constant offset; sensor outage/drop events can be scheduled as timeline events |
| **Traffic** | Persona schedules (Part 1, section 6) are defined on the virtual calendar (weekday/hour/holiday), so a Monday 09:00 episode looks different from Sunday 03:00. Agents read the virtual clock |
| **Attacks** | Campaign plan steps have virtual timestamps and an episode assignment. Dwell times between stages are sampled from realistic ranges |
| **GRC** | Bitemporal records (A8), changes as timeline events, as-of snapshots at episode starts |
| **Vulnerability intelligence** | See B8 |
| **Truth** | Controller logs written directly in virtual time from `VClock`, no conversion |

**Gaps are data, not silence.** Between episodes nothing is observed. The package includes `coverage_windows.json` listing observed windows (episodes) and unobserved gaps, so the Engine and the evaluation never confuse "not simulated" with "nothing happened". Layer 1 events during gaps are recorded in the change log (GRC and state), only raw telemetry is absent.

## B7. Time-consistency validator (runs per episode and per scenario)

```text
- every event timestamp falls inside its episode window (+ small drain tolerance)
- timestamps are monotonic per source and agree across sources within tolerance (Wazuh vs Suricata vs controller)
- no timestamp in the real current date or in 1970 (real-date leakage is a generator fingerprint)
- weekday/hour of activity matches the persona schedule for that virtual date
- GRC as-of snapshots contain no record with recorded_at after the snapshot time
- timeline events applied in order, none lost, none duplicated
- episode gap and offset values in the manifest match what the logs show
```
Failing validation rejects the episode and re-runs it (same seed), just like a failed health gate.

**Injected time imperfections (rare, ledgered, realistic):** a host with clock drift or wrong timezone, NTP outage, delayed log delivery, a few out-of-order events. These are deliberate sensor-quality facts recorded in `sensor_health.json` and the truth ledger, so the Engine can be tested on dirty timestamps, but the base timeline is always clean and known.

## B8. Time and vulnerability intelligence (avoiding future leakage)

Our enrichment snapshots (NVD, CISA KEV, EPSS) were taken at a real date. If a scenario's virtual date is earlier than data in the snapshot, using it unfiltered leaks the future (e.g. a CVE not yet published, a KEV entry added later).

Decision:
1. **Anchor virtual calendars in the past**, within a window ending at the snapshot date (e.g. 6-18 months before it). Then real history is replayed naturally: CVEs get published, KEV entries get added, at their real dates on our virtual timeline.
2. **Gate by date**: every intelligence field is filtered to `date <= virtual now`. NVD `published/modified`, KEV `dateAdded` are available; for EPSS only use values supported by dated data (EPSS historical files exist, to be verified [MEASURE]); if not available, expose EPSS only in the post-scenario retrospective snapshot.
3. Installed package versions in the range should be plausible for the virtual date (use distro snapshot archives, Part 1, section 3.3, matched to the scenario's virtual start).
4. The optional "live CVE feed" from the original spec runs **outside the range**: the same SBOM can be rescanned later against a fresher database to show how posture would have changed. It never changes the scenario itself.

## B9. Time budget reporting

Per scenario `run_metrics.json` records: virtual span, number of episodes, total virtual minutes observed, wall-clock per phase, **compression ratio** = virtual span / wall time, and Layer 1 event count. This gives honest numbers to present ("120 virtual days simulated in X hours, of which Y% observed in detail").

# PART C: FINAL DECISIONS (made)

1. GRC is derived from the spec as REALITY, then degraded to RECORDED. Engine sees only RECORDED.
2. v1 GRC scope: asset inventory, risk register, control register, policy exceptions (must), incident register and remediation tracker (small), framework mapping (lookup). Vendor register, audit findings, KRIs deferred, schema slots reserved.
3. Flaws are injected only on the recorded layer through modules with preconditions, levels L1-L5, detectability classes D1-D4 (D4 = 10% undetectable control group), maturity-driven rates, and a hidden ledger. Auto diff-audit guarantees no unexplained discrepancy.
4. Baseline human noise is bounded and separate from flaws.
5. GRC records are bitemporal; Engine gets as-of views only.
6. Organizational GRC style profile varies scales, vocabulary, frameworks and cadence per scenario, with a `scale_definition.json`.
7. Virtual time = two layers: instant state simulation + short real-time live episodes. Real services are never accelerated.
8. Episodes run at 1x with a constant clock offset (libfaketime offset mode first, constant post-shift for Suricata, retiming fallback).
9. v1 episode transition = deploy-from-state with persistent snapshot; the pause/jump optimization is adopted only if the clock-jump test passes.
10. Gaps between episodes are explicit (`coverage_windows.json`).
11. Virtual calendars are anchored in the past relative to the intelligence snapshot, and all enrichment is date-gated to prevent future leakage.
12. A single `VClock` is mandatory; the time-consistency validator gates every episode.
13. Seeds: `seed_time` and `seed_grc` added to the hierarchy. The master timeline and resolved GRC spec are stored in the package for replication.
